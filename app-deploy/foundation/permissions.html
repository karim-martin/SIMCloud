Permissions & Firewall Rules

Every IAM role, organization policy, firewall rule, and cluster access setting this guide depends on - in one place.

Read this before you run a single command

Most failed cloud deployments are not code problems. They are access problems: a missing IAM role, an organization policy that blocks the resource, or a firewall rule nobody opened. This page lists what has to be granted, by whom, and how to prove it worked before you get halfway through the build.

Four Identities, Four Permission Sets

The guide involves four distinct identities. Confusing them is the single most common source of "permission denied". Grant each one only what it needs.

IdentityWho or what it isUsed for
OperatorYou, signed in with gcloud auth loginCreating the project, VPC, cluster, database, and IAM bindings
CI/CD service accountgithub-actions-sa (or a Workload Identity Federation principal)Building images, pushing to Artifact Registry, rolling out Deployments
Workload service accountapp-workload-sa, bound to a Kubernetes SARuntime access to Cloud SQL, Cloud Storage, Secret Manager
Node service accountGKE node pool identityPulling images, writing logs and metrics from the node

These are the roles you need to complete the guide. In a personal sandbox project, roles/owner covers all of them. In a corporate environment you will usually be granted a subset, so check this list against what you actually have before you start - it is much cheaper to request access up front than to fail on step 40.

Grant Them

# Grant an operator the roles needed for this guide
export PROJECT_ID="my-app-project"
export OPERATOR="user:you@example.com"

for ROLE in \
  roles/serviceusage.serviceUsageAdmin \
  roles/compute.networkAdmin \
  roles/compute.securityAdmin \
  roles/servicenetworking.networksAdmin \
  roles/container.admin \
  roles/cloudsql.admin \
  roles/storage.admin \
  roles/artifactregistry.admin \
  roles/iam.serviceAccountAdmin \
  roles/resourcemanager.projectIamAdmin \
  roles/iam.workloadIdentityPoolAdmin \
  roles/secretmanager.admin
do
  gcloud projects add-iam-policy-binding "$PROJECT_ID" \
    --member="$OPERATOR" --role="$ROLE" --condition=None
done

Check What You Actually Have

# List every role bound to your account on this project
gcloud projects get-iam-policy "$PROJECT_ID" \
  --flatten="bindings[].members" \
  --filter="bindings.members:you@example.com" \
  --format="value(bindings.role)"

# Test a specific permission without needing to run the real command
gcloud projects test-iam-permissions "$PROJECT_ID" \
  --permissions=container.clusters.create,compute.firewalls.create,iam.serviceAccounts.create
Ask for the right thing

When you request access from a platform team, send them the table above rather than asking for "admin". A named list of roles scoped to one project is approved far more often than a blanket request, and it survives an audit.

2. Organization Policies That Can Block You

Organization policy constraints are inherited from the org or folder and override project-level IAM. You can hold every role in the table above and still be denied. Check these first in any corporate project.

# Inspect one constraint in detail
gcloud resource-manager org-policies describe \
  constraints/compute.vmExternalIpAccess --project="$PROJECT_ID" --effective

Do not run nodes as the default Compute Engine service account

The default service account carries roles/editor across the whole project. Any pod that reaches the node metadata endpoint inherits it. Create a dedicated node service account with only the four roles above and pass it with --service-account when you create the node pool.

# Dedicated node service account with minimal roles
gcloud iam service-accounts create gke-node-sa \
  --display-name="GKE Node Service Account"

export NODE_SA="gke-node-sa@${PROJECT_ID}.iam.gserviceaccount.com"

for ROLE in \
  roles/artifactregistry.reader \
  roles/logging.logWriter \
  roles/monitoring.metricWriter \
  roles/stackdriver.resourceMetadata.writer
do
  gcloud projects add-iam-policy-binding "$PROJECT_ID" \
    --member="serviceAccount:$NODE_SA" --role="$ROLE" --condition=None
done

# Use it when creating the node pool
gcloud container node-pools create default-pool \
  --cluster=app-cluster --region="$REGION" \
  --service-account="$NODE_SA" \
  --workload-metadata=GKE_METADATA

The Rule Everyone Forgets

Private cluster webhooks fail without this

On a private GKE cluster, GKE opens the control plane to nodes on ports 443 and 10250 only. Ingress controllers, cert-manager, Istio, and the Gateway API all register admission webhooks on other ports. Without the rule below, kubectl apply hangs and eventually fails with context deadline exceeded - and the error says nothing about firewalls.

# Find the control plane CIDR for your cluster
export MASTER_CIDR=$(gcloud container clusters describe app-cluster \
  --region="$REGION" \
  --format="value(privateClusterConfig.masterIpv4CidrBlock)")

# Allow the control plane to reach webhook ports on the nodes
gcloud compute firewall-rules create app-allow-master-webhooks \
  --network=app-vpc \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:8443,tcp:9443,tcp:15017 \
  --source-ranges="$MASTER_CIDR" \
  --target-tags=gke-node \
  --priority=1000 \
  --description="Control plane to admission webhooks"

If You Enforce Deny-All Egress

GCP allows all egress by default. If your security baseline replaces that with a deny-all rule, private nodes lose the ability to pull images, reach the control plane, and resolve DNS. These allow rules must sit at a higher priority than the deny.

DestinationPortsWhy
Control plane CIDRtcp:443kubelet to API server
199.36.153.4/30tcp:443restricted.googleapis.com - Artifact Registry, Logging, Monitoring via Private Google Access
169.254.169.254/32tcp:80, udp:53Metadata server and internal DNS
Pod and service CIDRsallPod-to-pod and pod-to-service traffic
Cloud SQL peering rangetcp:3307, tcp:5432, tcp:1433Database connections through the Auth Proxy
 
# Route Google APIs over Private Google Access instead of the internet
gcloud compute firewall-rules create app-allow-egress-google-apis \
  --network=app-vpc --direction=EGRESS --action=ALLOW \
  --rules=tcp:443 --destination-ranges=199.36.153.4/30 \
  --target-tags=gke-node --priority=1000

# Catch-all deny, logged, at the lowest priority
gcloud compute firewall-rules create app-deny-egress-all \
  --network=app-vpc --direction=EGRESS --action=DENY \
  --rules=all --destination-ranges=0.0.0.0/0 \
  --target-tags=gke-node --priority=65534 --enable-logging

5. Pod-Level Network Policy

Firewall rules stop at the node boundary. Inside the cluster, every pod can reach every other pod unless you say otherwise. Enable dataplane V2 and default-deny each namespace.

# Enable NetworkPolicy enforcement (Dataplane V2)
gcloud container clusters update app-cluster \
  --region="$REGION" --enable-dataplane-v2
# k8s/security/default-deny.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: app
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
# Frontend may reach the API; nothing else may
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: app
spec:
  podSelector:
    matchLabels: { app: dotnet-api }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: react-frontend }
      ports:
        - protocol: TCP
          port: 8080
---
# Every pod needs DNS even under a default deny
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-egress
  namespace: app
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53

6. Who Can Reach the Cluster API

Two independent gates control kubectl: a network gate (control plane authorized networks) and an identity gate (IAM plus Kubernetes RBAC). Both must pass.

Network Gate - Authorized Networks

# Restrict the control plane endpoint to known source ranges
gcloud container clusters update app-cluster \
  --region="$REGION" \
  --enable-master-authorized-networks \
  --master-authorized-networks=203.0.113.10/32,198.51.100.0/24

# Inspect the current allowlist
gcloud container clusters describe app-cluster --region="$REGION" \
  --format="value(masterAuthorizedNetworksConfig.cidrBlocks)"
GitHub Actions runners have no fixed IP

Hosted runners draw from a large, changing address pool, so you cannot allowlist them. Pick one of: a self-hosted runner inside the VPC, a Cloud Build private pool, or the gke-gcloud-auth-plugin against a cluster with a private endpoint reached through a bastion. Widening the allowlist to 0.0.0.0/0 defeats the control entirely.

Identity Gate - IAM and Kubernetes RBAC

An IAM role gets you to the API server. Kubernetes RBAC decides what you can do once you are there. roles/container.developer grants broad in-cluster edit rights; for anything narrower, grant roles/container.viewer and layer RBAC on top.

# Fetch credentials (requires roles/container.clusterViewer at minimum)
gcloud container clusters get-credentials app-cluster --region="$REGION"

# Namespace-scoped access for a developer, layered on roles/container.viewer
kubectl create rolebinding dev-edit \
  --clusterrole=edit \
  --user=dev@example.com \
  --namespace=app

# Confirm what an identity can actually do
kubectl auth can-i --list --namespace=app
kubectl auth can-i create deployments --namespace=app \
  --as=github-actions-sa@${PROJECT_ID}.iam.gserviceaccount.com

7. Pre-Flight Verification

Run this before you start building. Every line should succeed.

#!/usr/bin/env bash
set -euo pipefail
PROJECT_ID="${PROJECT_ID:?set PROJECT_ID}"
REGION="${REGION:-us-central1}"

echo "== Required APIs =="
for API in container sqladmin storage artifactregistry compute iam \
           iamcredentials secretmanager servicenetworking logging monitoring
do
  gcloud services list --enabled --project="$PROJECT_ID" \
    --filter="config.name:${API}.googleapis.com" --format="value(config.name)" \
    | grep -q . && echo "  OK   ${API}" || echo "  MISS ${API}"
done

echo "== Operator permissions =="
gcloud projects test-iam-permissions "$PROJECT_ID" --format="value(permissions)" \
  --permissions=container.clusters.create,compute.firewalls.create,\
compute.networks.create,cloudsql.instances.create,iam.serviceAccounts.create,\
resourcemanager.projects.setIamPolicy,artifactregistry.repositories.create

echo "== Organization policies in force =="
gcloud resource-manager org-policies list --project="$PROJECT_ID"

echo "== Firewall rules =="
gcloud compute firewall-rules list --project="$PROJECT_ID" \
  --filter="network:app-vpc" \
  --format="table(name,direction,priority,sourceRanges.list(),allowed[].map().firewall_rule().list())"
