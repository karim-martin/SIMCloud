Permissions & Security Groups

AWS

Every IAM policy, EKS access entry, and security group rule this guide depends on - in one place.

Read this before you run a single command

On AWS, access is enforced in four independent layers: IAM decides what your identity may call, service control policies can override IAM at the organization level, security groups decide what traffic may flow, and EKS access entries decide who kubectl will listen to. A deployment fails if any one of them says no, and the error rarely tells you which one.

Six Identities, Six Permission Sets

The Account Setup page attaches AdministratorAccess to get you moving. That is fine for a sandbox account and unacceptable in a shared one. Here is what the deployer actually needs.

iam:PassRole is the one people forget

Creating a cluster or node group means handing an existing IAM role to another AWS service. Without iam:PassRole for that specific role ARN, eksctl and Terraform fail with an authorization error that names the caller rather than the missing action. Scope it to the role ARNs you created, never to *.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PassClusterAndNodeRoles",
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": [
        "arn:aws:iam::123456789012:role/eksClusterRole",
        "arn:aws:iam::123456789012:role/eksNodeRole"
      ],
      "Condition": {
        "StringEquals": {
          "iam:PassedToService": [
            "eks.amazonaws.com",
            "ec2.amazonaws.com"
          ]
        }
      }
    },
    {
      "Sid": "DenyIamOutsideThisProject",
      "Effect": "Deny",
      "Action": ["iam:CreateUser", "iam:CreateAccessKey", "iam:DeleteRole"],
      "Resource": "*"
    }
  ]
}

Prefer OIDC Over Long-Lived Keys

Access keys in GitHub secrets are the most common credential leak in this whole pipeline. Federate instead - GitHub presents an OIDC token, AWS returns short-lived credentials, and there is nothing to rotate or leak.

# Trust policy for the GitHub Actions deploy role
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
      },
      "StringLike": {
        "token.actions.githubusercontent.com:sub": "repo:my-org/my-repo:ref:refs/heads/main"
      }
    }
  }]
}
Pin the sub condition

A trust policy with sub set to repo:my-org/* lets any branch in any repository in your organization assume the role - including a branch opened by a fork-based pull request. Pin it to the exact repository and ref, or to environment:production and require an approval on that environment.

Move the CNI policy to IRSA

AmazonEKS_CNI_Policy on the node role means every pod on the node can reach those EC2 APIs through the instance metadata endpoint. Attach it to an IRSA role for the aws-node service account instead, and set the metadata hop limit to 1 so pods cannot reach IMDS at all.

4. Who Can Run kubectl - EKS Access Entries

IAM alone does not get you into the cluster

The identity that created the cluster is the only one with in-cluster admin by default. A colleague holding AdministratorAccess still gets error: You must be logged in to the server (Unauthorized). You have to map their IAM principal into Kubernetes explicitly. This trips up nearly every team on their first EKS cluster.

Access Entries (Current Approach)

EKS clusters running the API or API_AND_CONFIG_MAP authentication mode use the access entry API. This is the approach to use for anything new - it is auditable through CloudTrail and cannot be corrupted by a bad ConfigMap edit.

# Confirm which authentication mode the cluster uses
aws eks describe-cluster --name myapp-cluster \
  --query "cluster.accessConfig.authenticationMode" --output text

# Give a platform engineer cluster admin
aws eks create-access-entry \
  --cluster-name myapp-cluster \
  --principal-arn arn:aws:iam::123456789012:role/PlatformEngineer \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name myapp-cluster \
  --principal-arn arn:aws:iam::123456789012:role/PlatformEngineer \
  --access-scope type=cluster \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy

# Give the CI/CD role edit rights on one namespace only
aws eks create-access-entry \
  --cluster-name myapp-cluster \
  --principal-arn arn:aws:iam::123456789012:role/GitHubActionsDeploy \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name myapp-cluster \
  --principal-arn arn:aws:iam::123456789012:role/GitHubActionsDeploy \
  --access-scope type=namespace,namespaces=app \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy

# Audit who has access
aws eks list-access-entries --cluster-name myapp-cluster
Access policyGrantsGive it to
AmazonEKSClusterAdminPolicyFull cluster-adminPlatform engineers, break-glass only
AmazonEKSAdminPolicyAdmin within a namespaceTeam leads owning a namespace
AmazonEKSEditPolicyCreate and update workloadsCI/CD deploy roles, developers
AmazonEKSViewPolicyRead-onlySupport, on-call, auditors

aws-auth ConfigMap (Legacy Clusters)

Clusters still in CONFIG_MAP mode map principals through a ConfigMap in kube-system. Edit it carefully - a malformed entry locks everyone out, and there is no undo.

kubectl edit configmap aws-auth -n kube-system
apiVersion: v1
kind: ConfigMap
metadata:
  name: aws-auth
  namespace: kube-system
data:
  # Do not remove this entry - nodes will stop joining the cluster
  mapRoles: |
    - rolearn: arn:aws:iam::123456789012:role/eksNodeRole
      username: system:node:{{EC2PrivateDNSName}}
      groups:
        - system:bootstrappers
        - system:nodes
    - rolearn: arn:aws:iam::123456789012:role/GitHubActionsDeploy
      username: github-actions
      groups:
        - app-deployers
  mapUsers: |
    - userarn: arn:aws:iam::123456789012:user/alice
      username: alice
      groups:
        - system:masters
# Back it up before every edit
kubectl get configmap aws-auth -n kube-system -o yaml > aws-auth-backup.yaml

# Bind the custom group to real Kubernetes permissions
kubectl create rolebinding app-deployers-edit \
  --clusterrole=edit --group=app-deployers --namespace=app

# Verify from the caller's perspective
aws sts get-caller-identity
kubectl auth can-i --list --namespace=app
Migrating off aws-auth

Switch to API_AND_CONFIG_MAP first, recreate every mapping as an access entry, confirm each principal still works, and only then move to API. The switch is one-way - you cannot go back to CONFIG_MAP.

5. Security Group Rules Required

Security groups are stateful, so a rule allowing inbound traffic automatically permits the response. Reference other security groups by ID rather than by CIDR - the rule then follows the resources as they scale and stays correct when subnet ranges change.

Security groupDirectionSource or destinationPortPurpose
alb-sgInbound0.0.0.0/0443Public HTTPS
Inbound0.0.0.0/080HTTP, redirected to HTTPS at the listener
Outboundnode-sg1025-65535Forward to node ports and pod targets
node-sg (cluster security group)Inboundalb-sg1025-65535Traffic from the load balancer
Inboundnode-sg (itself)allPod-to-pod, CoreDNS on 53 TCP and UDP
Inboundcontrol-plane-sg10250API server to kubelet - logs and exec
Inboundcontrol-plane-sg443, 8443, 9443Admission and conversion webhooks
Outbound0.0.0.0/0443ECR, STS, and AWS APIs - or restrict to VPC endpoints
control-plane-sgInboundnode-sg443kubelet to API server
Outboundnode-sg10250, 443, 8443, 9443API server to kubelet and webhooks
rds-sgInboundnode-sg only1433 (SQL Server) or 5432 (PostgreSQL)Application to database
redis-sgInboundnode-sg only6379ElastiCache
vpce-sgInboundnode-sg443Interface VPC endpoints
Never put 0.0.0.0/0 on the database security group

An RDS instance in a public subnet with an open security group is discoverable by internet-wide scanners within minutes. The database security group should reference node-sg and nothing else - no CIDR blocks, no office IP ranges, no bastion exceptions. Use Session Manager port forwarding when a human needs a shell.

Terraform

# The EKS cluster security group, created by the module
data "aws_eks_cluster" "this" {
  name = module.eks.cluster_name
}

locals {
  node_sg_id = module.eks.node_security_group_id
}

# ALB security group
resource "aws_security_group" "alb" {
  name        = "myapp-alb-sg"
  description = "Public ingress to the application load balancer"
  vpc_id      = module.vpc.vpc_id

  ingress {
    description = "HTTPS from the internet"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  ingress {
    description = "HTTP, redirected to HTTPS"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }

  egress {
    description     = "Forward to node targets"
    from_port       = 1025
    to_port         = 65535
    protocol        = "tcp"
    security_groups = [local.node_sg_id]
  }
}

# Let the ALB reach the nodes
resource "aws_security_group_rule" "nodes_from_alb" {
  description              = "ALB to node targets"
  type                     = "ingress"
  from_port                = 1025
  to_port                  = 65535
  protocol                 = "tcp"
  security_group_id        = local.node_sg_id
  source_security_group_id = aws_security_group.alb.id
}

# Database reachable only from the nodes
resource "aws_security_group" "rds" {
  name        = "myapp-rds-sg"
  description = "Database access restricted to EKS nodes"
  vpc_id      = module.vpc.vpc_id

  ingress {
    description     = "SQL Server from EKS nodes only"
    from_port       = 1433
    to_port         = 1433
    protocol        = "tcp"
    security_groups = [local.node_sg_id]
  }
}

# Admission webhooks from the control plane
resource "aws_security_group_rule" "nodes_webhooks_from_control_plane" {
  description              = "Control plane to admission webhooks"
  type                     = "ingress"
  from_port                = 8443
  to_port                  = 9443
  protocol                 = "tcp"
  security_group_id        = local.node_sg_id
  source_security_group_id = module.eks.cluster_security_group_id
}

Network ACLs

NACLs are stateless and evaluated per subnet before security groups. The default NACL allows everything, which is usually correct. If your organization replaces it with a restrictive one, remember that return traffic needs its own rule - allow inbound on ephemeral ports 1024-65535, or every outbound connection will hang instead of failing fast.

If nodes have no NAT gateway or your egress is locked down, these endpoints are mandatory. Without them nodes cannot pull images or fetch credentials, and they fail during bootstrap with timeouts rather than access errors.

Interface endpoints are not free

Each interface endpoint costs roughly $7 per AZ per month plus data processing. Ten endpoints across three AZs is around $220 a month - often more than the NAT gateway it replaces. Choose based on your security requirement, not on cost alone, and always take the free S3 gateway endpoint.

7. Pod-Level Network Policy

Security groups control traffic at the ENI. Inside the cluster, pod-to-pod traffic is unrestricted until you install a policy engine. The VPC CNI supports NetworkPolicy natively from version 1.14.

# Enable NetworkPolicy in the VPC CNI add-on
aws eks update-addon --cluster-name myapp-cluster \
  --addon-name vpc-cni \
  --configuration-values '{"enableNetworkPolicy":"true"}'
# k8s/security/default-deny.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: app
spec:
  podSelector: {}
  policyTypes: [Ingress]
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: app
spec:
  podSelector:
    matchLabels: { app: dotnet-api }
  policyTypes: [Ingress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: react-frontend }
      ports:
        - protocol: TCP
          port: 8080

8. Organization Guardrails

Service control policies apply to every principal in the account including the root user, and they are evaluated before IAM. If an SCP denies an action, no IAM policy can restore it.

Common SCPEffect on this guideHow to proceed
Region restrictionCluster creation denied outside approved regionsSet your region to an approved one before starting
Deny public S3 bucketsBucket ACL and public policy calls failAlready compatible - serve assets through CloudFront with OAC
Require EBS encryptionUnencrypted volume creation deniedSet encrypted = true on the node group launch template
Deny IAM user creationaws iam create-user failsUse IAM Identity Center and OIDC federation instead
Deny internet gateway changesVPC module cannot create the IGWAsk the network team to provision the VPC and pass in the IDs
Require resource tagsUntagged resource creation deniedSet default_tags in the AWS Terraform provider block

9. Pre-Flight Verification

#!/usr/bin/env bash
set -euo pipefail
CLUSTER="${CLUSTER:-myapp-cluster}"
REGION="${AWS_REGION:-us-east-1}"

echo "== Caller identity =="
aws sts get-caller-identity

echo "== Can the deployer perform the key actions? =="
PRINCIPAL=$(aws sts get-caller-identity --query Arn --output text)
aws iam simulate-principal-policy \
  --policy-source-arn "$PRINCIPAL" \
  --action-names eks:CreateCluster ec2:CreateVpc iam:CreateRole \
                 iam:PassRole rds:CreateDBInstance ecr:CreateRepository \
  --query "EvaluationResults[].{Action:EvalActionName,Decision:EvalDecision}" \
  --output table

echo "== OIDC provider for IRSA =="
aws eks describe-cluster --name "$CLUSTER" --region "$REGION" \
  --query "cluster.identity.oidc.issuer" --output text

echo "== Who can reach the cluster =="
aws eks list-access-entries --cluster-name "$CLUSTER" --region "$REGION"

echo "== Security groups on the cluster =="
aws ec2 describe-security-groups --region "$REGION" \
  --filters "Name=tag:kubernetes.io/cluster/${CLUSTER},Values=owned" \
  --query "SecurityGroups[].{Name:GroupName,Id:GroupId}" --output table

echo "== Anything open to the world on a database port? =="
aws ec2 describe-security-groups --region "$REGION" \
  --query "SecurityGroups[?IpPermissions[?contains(to_string(IpRanges[].CidrIp), '0.0.0.0/0') \
           && (FromPort==\`1433\` || FromPort==\`5432\` || FromPort==\`3306\`)]].GroupId" \
  --output text
