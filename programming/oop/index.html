Object-Oriented Programming (OOP)

OOP organises a program around objects - self-contained bundles of data and the behaviour that acts on that data.

OOP in one sentence

Instead of writing a program as a long list of instructions that push loose variables around, you group related data and the code that works on it into objects, and let those objects talk to each other.

The problem OOP solves

Imagine a program that tracks bank accounts. Without objects, you keep the data in loose variables and write functions that operate on them:

// Procedural style - data and behaviour are separate
string ownerName = "Ada";
decimal balance = 500m;

void Deposit(ref decimal bal, decimal amount)
{
    bal += amount;
}

Deposit(ref balance, 100m);
Console.WriteLine(balance);   // 600

This works for one account. Now add a second account, then a third, then interest rates, overdraft limits, and transaction history. You end up with:

  • Loose variables everywhere. balance1, balance2, ownerName1... nothing ties them together.
  • No protection. Any line of code anywhere can write balance = -999999. Nothing stops it.
  • Rules scattered. The "you cannot withdraw more than you have" check gets copy-pasted into five places, and one of the copies is wrong.

The same thing with objects

An object keeps the data and the rules together. The balance can only change through methods you wrote, and those methods enforce the rules every time:

public class BankAccount
{
    // Data: private, so only this class can touch it directly
    private decimal _balance;

    public string OwnerName { get; }

    public BankAccount(string ownerName, decimal openingBalance)
    {
        OwnerName = ownerName;
        _balance = openingBalance;
    }

    // Behaviour: the only way in, and it enforces the rules
    public void Deposit(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentException("Deposit must be positive.");
        _balance += amount;
    }

    public bool TryWithdraw(decimal amount)
    {
        if (amount <= 0 || amount > _balance)
            return false;                 // rule lives in exactly one place
        _balance -= amount;
        return true;
    }

    public decimal GetBalance() => _balance;
}
// Each account is a separate object with its own state
var ada = new BankAccount("Ada", 500m);
var alan = new BankAccount("Alan", 20m);

ada.Deposit(100m);
Console.WriteLine(ada.GetBalance());      // 600
Console.WriteLine(alan.GetBalance());     // 20   - untouched

bool ok = alan.TryWithdraw(1000m);
Console.WriteLine(ok);                    // False - rule enforced
// alan._balance = 1_000_000;             // will not compile: _balance is private
The shift in thinking

Procedural code asks "what steps do I run?". Object-oriented code asks "what things exist, what does each one know, and what can each one do?". Nouns become classes; verbs become methods.

The vocabulary

Two groups of ideas. The building blocks are the physical parts you type; the four pillars are the principles that tell you how to arrange them.

TermGroupPlain English
ClassBuilding blockA blueprint that defines structure and behaviour.
ObjectBuilding blockOne thing built from that blueprint, holding its own state.
Attribute (field / property)Building blockA piece of data an object holds.
MethodBuilding blockAn operation that acts on that data.
Message passingBuilding blockOne object invoking another object's method.
Constructor / destructorBuilding blockCode that runs when an object is created and when it is cleaned up.
EncapsulationPillarBundle data with its methods; block direct access to internals.
AbstractionPillarExpose essential behaviour; hide implementation detail.
InheritancePillarDerive a class from another to reuse and extend behaviour.
PolymorphismPillarOne interface, many implementations.

What you get out of it

BenefitWhat it means day to day
Fewer bugsRules are enforced in one place, so they cannot drift out of sync.
Easier changeRewrite how a class stores its data without touching any calling code.
ReuseA well-written class is used across features, projects, and NuGet packages.
TestabilityDepend on interfaces, swap in a fake implementation, and unit test without a database.
Shared language"Order", "Invoice", "Customer" mean the same thing in the code and in the business.
OOP is a tool, not a religion

Not everything needs to be a class. A pure calculation is fine as a static method, and modern C# leans on records, LINQ, and functional style for data transformation. Use objects where state and rules live together; use plain functions where they do not.
