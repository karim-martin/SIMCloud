Pillar 3: Inheritance

Build a new class on top of an existing one, keeping what fits and changing what does not.

Inheritance in one sentence

A new class starts as a copy of an existing one - it gets all that class's members for free - and then adds to or changes whatever it needs. The original is the base class; the new one is the derived class.

The syntax

A colon means "derives from". The derived class automatically has everything the base class has.

public class Animal
{
    public string Name { get; set; }

    public void Eat()
    {
        Console.WriteLine($"{Name} is eating.");
    }
}

// Dog IS AN Animal - it inherits Name and Eat()
public class Dog : Animal
{
    public void Bark()
    {
        Console.WriteLine($"{Name} says woof!");   // Name came from Animal
    }
}
var dog = new Dog { Name = "Rex" };
dog.Eat();    // Rex is eating.   - inherited, not written in Dog
dog.Bark();   // Rex says woof!   - added by Dog

Animal asAnimal = dog;             // a Dog can be used anywhere an Animal is expected
asAnimal.Eat();                    // Rex is eating.
// asAnimal.Bark();                // compile error: Animal has no Bark()

What is and is not inherited

MemberInherited?Note
public membersYesFully usable by the derived class and its callers
protected membersYesUsable inside the derived class, not by outside callers
internal membersYes, within the same assemblyInvisible to derived classes in other projects
private membersPresent but not accessibleThe field still exists in memory; the derived class cannot name it
ConstructorsNoBut a derived constructor must call one, via base(...)
FinalizersNoEach class declares its own, and the chain is run automatically
Static membersAccessible through the derived nameThere is still only one copy, on the base class

Constructors and the base keyword

Constructing a derived object always constructs the base part first. If the base class has no parameterless constructor, the derived constructor must say which base constructor to call.

public class Employee
{
    public string Name { get; }
    public decimal BaseSalary { get; }

    public Employee(string name, decimal baseSalary)
    {
        Name = name;
        BaseSalary = baseSalary;
        Console.WriteLine("Employee constructor ran.");
    }

    public virtual decimal MonthlyPay() => BaseSalary / 12;
}

public class Manager : Employee
{
    public decimal Bonus { get; }

    // ": base(...)" passes arguments up to the Employee constructor
    public Manager(string name, decimal baseSalary, decimal bonus)
        : base(name, baseSalary)
    {
        Bonus = bonus;
        Console.WriteLine("Manager constructor ran.");
    }

    // "override" replaces the base behaviour...
    public override decimal MonthlyPay()
    {
        // ...and "base." calls the version we replaced, so we can build on it
        return base.MonthlyPay() + (Bonus / 12);
    }
}
var manager = new Manager("Ada", 120_000m, 24_000m);
// Employee constructor ran.      <- base runs FIRST
// Manager constructor ran.

Console.WriteLine(manager.MonthlyPay());   // 12000  = 10000 base + 2000 bonus

virtual, override, sealed, and new

A base method is only replaceable if it says so. Four keywords control this:

KeywordWhereMeaning
virtualBase method"Subclasses may replace me."
overrideDerived method"I am the replacement." Called even through a base-typed variable.
abstractBase method (in an abstract class)"I have no body; subclasses must supply one."
sealed overrideDerived method"No further subclass may override this."
newDerived methodHides rather than overrides - usually a mistake. See below.
new hides, override replaces

This distinction bites every beginner. With override, the object's real type decides which method runs. With new, the variable's declared type decides - so the same object behaves differently depending on how you are holding it.

public class Base
{
    public virtual string Virtual() => "Base.Virtual";
    public string NonVirtual()      => "Base.NonVirtual";
}

public class Derived : Base
{
    public override string Virtual() => "Derived.Virtual";
    public new string NonVirtual()   => "Derived.NonVirtual";   // hides, not overrides
}

Derived d = new Derived();
Base    b = d;                       // SAME object, different variable type

Console.WriteLine(d.Virtual());      // Derived.Virtual
Console.WriteLine(b.Virtual());      // Derived.Virtual     <- override: real type wins
Console.WriteLine(d.NonVirtual());   // Derived.NonVirtual
Console.WriteLine(b.NonVirtual());   // Base.NonVirtual     <- new: variable type wins

Almost always you want virtual + override. If the compiler warns that a member hides an inherited one, do not silence it with new - rename your method or make the base member virtual.

sealed

// A sealed class cannot be inherited from at all
public sealed class TaxCalculator { }
// public class UkTaxCalculator : TaxCalculator { }   // compile error

public class Middle : Base
{
    // Overrides Base.Virtual, and stops anyone below from overriding it again
    public sealed override string Virtual() => "Middle.Virtual";
}

Everything inherits from object

Every C# type, even one with no : in its declaration, ultimately derives from System.Object. That is where ToString(), Equals(), and GetHashCode() come from - and overriding them is often the first useful override you write.

public class Point
{
    public int X { get; }
    public int Y { get; }
    public Point(int x, int y) { X = x; Y = y; }

    // Without this, Console.WriteLine(point) prints the type name
    public override string ToString() => $"({X}, {Y})";

    // Value equality instead of reference equality
    public override bool Equals(object? obj) =>
        obj is Point other && other.X == X && other.Y == Y;

    // Equals and GetHashCode must always be overridden together
    public override int GetHashCode() => HashCode.Combine(X, Y);
}

var p1 = new Point(1, 2);
var p2 = new Point(1, 2);
Console.WriteLine(p1);                 // (1, 2)
Console.WriteLine(p1.Equals(p2));      // True

Multi-level inheritance

public class Vehicle
{
    public int Wheels { get; protected set; } = 4;
    public virtual string Describe() => $"A vehicle with {Wheels} wheels";
}

public class MotorVehicle : Vehicle
{
    public int EngineCc { get; protected set; }
    public override string Describe() => base.Describe() + $", engine {EngineCc}cc";
}

public class Motorcycle : MotorVehicle
{
    public Motorcycle()
    {
        Wheels = 2;          // allowed: the setter is protected
        EngineCc = 650;
    }

    public override string Describe() => base.Describe() + ", and it leans in corners";
}

Console.WriteLine(new Motorcycle().Describe());
// A vehicle with 2 wheels, engine 650cc, and it leans in corners
Keep hierarchies shallow

Two or three levels is usually plenty. Once a chain is five deep, understanding what any given method does means opening five files, and a change to the top ripples through all of them. This is called the fragile base class problem.

C# has no multiple inheritance

A class may have only one base class, but may implement any number of interfaces. This avoids the "diamond problem" (two base classes offering the same method, and no rule for which one wins).

public interface ISwimmer { void Swim(); }
public interface IFlyer   { void Fly(); }

// One base class, as many interfaces as you like
public class Duck : Animal, ISwimmer, IFlyer
{
    public void Swim() => Console.WriteLine($"{Name} paddles.");
    public void Fly()  => Console.WriteLine($"{Name} flies away.");
}

// public class Impossible : Animal, Vehicle { }   // compile error: two base classes

Inheritance vs composition

The most common design mistake with inheritance is using it for code reuse when there is no real "is a" relationship. The alternative is composition: hold an instance of the other class instead of inheriting from it.

// WRONG - a Car is not a kind of Engine, so this makes no sense
public class Car : Engine { }

// RIGHT - a Car HAS AN Engine
public class Engine
{
    public void Start() => Console.WriteLine("Vroom.");
}

public class Car
{
    private readonly Engine _engine = new();

    public void Start() => _engine.Start();     // delegate to the part it owns
}
QuestionIf yes
Is a Dog genuinely a kind of Animal?Inheritance
Does a Car merely contain an Engine?Composition
Do you want the base class's public API to become yours?Inheritance
Do you only want to reuse a couple of its methods?Composition
Must the relationship be swappable at runtime?Composition (against an interface)
"Favour composition over inheritance"

The classic advice, and it holds up. Inheritance is a permanent, compile-time bond that exposes the whole base API to your callers. Composition is a private, swappable relationship you control. Reach for inheritance when the "is a" is real and you want polymorphism; otherwise compose.

The substitution test

Before you inherit, check the Liskov Substitution Principle: anywhere the base type is used, a derived object must work without surprising the caller. The classic failure:

public class Rectangle
{
    public virtual int Width { get; set; }
    public virtual int Height { get; set; }
    public int Area => Width * Height;
}

// A square IS a rectangle in mathematics, but not as a mutable class
public class Square : Rectangle
{
    public override int Width
    {
        get => base.Width;
        set { base.Width = value; base.Height = value; }
    }

    public override int Height
    {
        get => base.Height;
        set { base.Width = value; base.Height = value; }
    }
}

void Resize(Rectangle r)
{
    r.Width = 5;
    r.Height = 4;
    Console.WriteLine(r.Area);      // caller expects 20
}

Resize(new Rectangle());            // 20  - as expected
Resize(new Square());               // 16  - the contract is broken

The fix is not clever code - it is to stop inheriting. Make Square and Rectangle separate immutable types, or give them a common IShape interface exposing only Area.

Checklist

DoAvoid
Inherit only for a genuine "is a"Inheriting just to reuse two methods
Mark extension points virtual or abstract deliberatelyMaking everything virtual by reflex
Call base.Method() when extending behaviourSilently dropping the base behaviour
Use protected for members subclasses needMaking fields public so subclasses can reach them
Keep hierarchies two or three levels deepDeep chains nobody can follow
sealed classes not designed for inheritanceLeaving every class open by accident
