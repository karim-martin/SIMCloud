Pillar 2: Abstraction

Show what an object does. Hide how it does it.

Abstraction in one sentence

You drive a car with a steering wheel, three pedals, and a gear selector. You do not need to know about fuel injection or valve timing. The controls are the abstraction; the engine is the implementation.

Abstraction vs encapsulation

These two are constantly confused because they overlap. The difference is what problem each one solves:

EncapsulationAbstraction
Question it answers"Who is allowed to change this data?""What does the caller need to know about?"
ConcernProtecting state from misuseSimplifying the model presented to callers
Toolsprivate, properties, validationabstract classes, interfaces, method names
LevelInside one classAcross a design
SloganHide the dataHide the complexity

They work together: encapsulation is largely how you achieve abstraction inside a single class.

Abstraction starts with method names

You do not need any special keyword to abstract. A well-named method that hides ten messy steps behind one clear call is already abstraction:

public class PasswordHasher
{
    // The caller sees one simple operation...
    public string Hash(string password)
    {
        byte[] salt = GenerateSalt();
        byte[] hash = DeriveKey(password, salt);
        return Encode(salt, hash);
    }

    public bool Verify(string password, string stored)
    {
        (byte[] salt, byte[] expected) = Decode(stored);
        byte[] actual = DeriveKey(password, salt);
        return CryptographicOperations.FixedTimeEquals(actual, expected);
    }

    // ...and none of this: iteration counts, salt sizes, encoding format
    private static byte[] GenerateSalt() => RandomNumberGenerator.GetBytes(16);

    private static byte[] DeriveKey(string password, byte[] salt) =>
        Rfc2898DeriveBytes.Pbkdf2(password, salt, 210_000, HashAlgorithmName.SHA256, 32);

    private static string Encode(byte[] salt, byte[] hash) =>
        $"{Convert.ToBase64String(salt)}.{Convert.ToBase64String(hash)}";

    private static (byte[] salt, byte[] hash) Decode(string stored)
    {
        string[] parts = stored.Split('.');
        return (Convert.FromBase64String(parts[0]), Convert.FromBase64String(parts[1]));
    }
}
var hasher = new PasswordHasher();
string stored = hasher.Hash("correct horse battery staple");
Console.WriteLine(hasher.Verify("correct horse battery staple", stored));  // True
Console.WriteLine(hasher.Verify("wrong password", stored));                // False

If the security team later raises the iteration count, every caller keeps working unchanged. That is the value: the abstraction stayed the same while the implementation moved.

Abstract classes

An abstract class describes a partially built idea. It cannot be instantiated - it exists to be inherited from. It can mix abstract members (a signature with no body, which every subclass must supply) with concrete members (shared code all subclasses inherit).

public abstract class PaymentMethod
{
    protected PaymentMethod(string reference) => Reference = reference;

    public string Reference { get; }

    // Abstract: no body. Every subclass MUST implement this.
    public abstract bool Authorise(decimal amount);

    // Abstract: each method knows its own fee structure.
    public abstract decimal CalculateFee(decimal amount);

    // Concrete: shared logic, written once, inherited by every subclass.
    public string Describe(decimal amount) =>
        $"{GetType().Name} {Reference}: {amount:C} + {CalculateFee(amount):C} fee";
}
public class CreditCardPayment : PaymentMethod
{
    private readonly decimal _limit;

    public CreditCardPayment(string reference, decimal limit) : base(reference)
        => _limit = limit;

    public override bool Authorise(decimal amount) => amount <= _limit;

    public override decimal CalculateFee(decimal amount) => Math.Round(amount * 0.029m, 2);
}

public class BankTransferPayment : PaymentMethod
{
    public BankTransferPayment(string reference) : base(reference) { }

    public override bool Authorise(decimal amount) => amount > 0;

    public override decimal CalculateFee(decimal amount) => 0.30m;   // flat fee
}
// var p = new PaymentMethod("X");    // compile error: cannot instantiate abstract class

var card = new CreditCardPayment("****4242", limit: 1000m);
Console.WriteLine(card.Describe(200m));    // CreditCardPayment ****4242: £200.00 + £5.80 fee
Console.WriteLine(card.Authorise(5000m));  // False

var transfer = new BankTransferPayment("SORT-12-34-56");
Console.WriteLine(transfer.Describe(200m)); // BankTransferPayment SORT-...: £200.00 + £0.30 fee

Interfaces

An interface is a pure contract: a list of members a class promises to provide, with no state and (traditionally) no implementation. Where an abstract class says "is a kind of", an interface says "is capable of".

public interface INotificationSender
{
    string Channel { get; }
    Task SendAsync(string recipient, string message);
}
public class EmailSender : INotificationSender
{
    public string Channel => "Email";

    public Task SendAsync(string recipient, string message)
    {
        Console.WriteLine($"[SMTP] to {recipient}: {message}");
        return Task.CompletedTask;
    }
}

public class SmsSender : INotificationSender
{
    public string Channel => "SMS";

    public Task SendAsync(string recipient, string message)
    {
        // Truncation is an SMS concern - callers never see it
        string trimmed = message.Length > 160 ? message[..157] + "..." : message;
        Console.WriteLine($"[SMS] to {recipient}: {trimmed}");
        return Task.CompletedTask;
    }
}

public class SlackSender : INotificationSender
{
    public string Channel => "Slack";

    public Task SendAsync(string recipient, string message)
    {
        Console.WriteLine($"[Slack] @{recipient}: {message}");
        return Task.CompletedTask;
    }
}

Now the code that sends alerts depends only on the contract. It never mentions SMTP, SMS, or Slack:

public class AlertService
{
    private readonly IEnumerable<INotificationSender> _senders;

    public AlertService(IEnumerable<INotificationSender> senders) => _senders = senders;

    public async Task RaiseAsync(string recipient, string message)
    {
        foreach (INotificationSender sender in _senders)
        {
            Console.WriteLine($"Sending via {sender.Channel}...");
            await sender.SendAsync(recipient, message);
        }
    }
}

var alerts = new AlertService(new INotificationSender[]
{
    new EmailSender(), new SmsSender(), new SlackSender()
});

await alerts.RaiseAsync("ada", "Disk usage above 90%");
The test that proves the abstraction works

Adding a fourth channel - Microsoft Teams, say - means writing one new class. AlertService is not touched, not recompiled in your head, not re-tested. Code that is open to extension but closed to modification is the goal.

Why interfaces make testing easy

Depending on an interface lets a test substitute a fake implementation, so you can test logic without a real database, network, or mail server:

// A fake that records what it was asked to do
public class FakeSender : INotificationSender
{
    public List<string> Sent { get; } = new();
    public string Channel => "Fake";

    public Task SendAsync(string recipient, string message)
    {
        Sent.Add($"{recipient}|{message}");
        return Task.CompletedTask;
    }
}

// The test - fast, deterministic, no infrastructure
var fake = new FakeSender();
var service = new AlertService(new[] { fake });
await service.RaiseAsync("ada", "Disk full");

Console.WriteLine(fake.Sent.Count);      // 1
Console.WriteLine(fake.Sent[0]);         // ada|Disk full

Rule of thumb

Default to an interface. Reach for an abstract class when several implementations genuinely share code and state. You can use both: an interface for the contract, an abstract base class implementing the common parts of it.

// Both together - a common pattern in real code
public interface IReportExporter
{
    string Extension { get; }
    byte[] Export(IReadOnlyList<string> rows);
}

public abstract class ReportExporterBase : IReportExporter
{
    public abstract string Extension { get; }

    public byte[] Export(IReadOnlyList<string> rows)
    {
        Validate(rows);                         // shared behaviour
        string content = Render(rows);          // subclass-specific step
        return System.Text.Encoding.UTF8.GetBytes(content);
    }

    protected abstract string Render(IReadOnlyList<string> rows);

    private static void Validate(IReadOnlyList<string> rows)
    {
        if (rows.Count == 0) throw new ArgumentException("Nothing to export.");
    }
}

public class CsvExporter : ReportExporterBase
{
    public override string Extension => ".csv";
    protected override string Render(IReadOnlyList<string> rows) => string.Join("\n", rows);
}
That last example is the Template Method pattern

The base class fixes the order of the steps (validate, then render, then encode) and lets subclasses fill in one step. You will meet it often once you start reading framework source.

Layers of abstraction in a real app

Each layer hides the one below it
Controller
Knows about HTTP, not SQL
calls IOrderService
Service
Knows business rules, not storage
calls IOrderRepository
Repository
Knows SQL, not business rules
ADO.NET / EF Core
Database
Knows only tables

Swapping the database means rewriting one repository class. Nothing above it changes - because nothing above it ever knew what the database was.
