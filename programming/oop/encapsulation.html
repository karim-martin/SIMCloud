Pillar 1: Encapsulation

Keep the data and the code that changes it together, and let nobody reach in from outside.

Encapsulation in one sentence

Put the data and the code that changes it in the same class, then make the data private so the only way to change it is through methods that enforce your rules. Think of a vending machine: you press a button, you do not reach inside.

The problem: unguarded data

Here is a class with public fields. It compiles, it runs, and it is a bug waiting to happen:

// BAD - anyone can put this object into a nonsense state
public class BankAccount
{
    public decimal Balance;
    public bool IsClosed;
}

var account = new BankAccount { Balance = 100m };
account.Balance = -50_000m;     // nothing stops this
account.IsClosed = true;
account.Balance += 10m;         // deposit into a closed account - also fine

Two things are wrong. First, the rules ("balance never goes negative", "no deposits into a closed account") exist only in your head. Second, when a negative balance turns up in production, the culprit could be any line in the entire codebase.

The fix: private data, public behaviour

public class BankAccount
{
    // 1. State is private - unreachable from outside the class
    private decimal _balance;
    private bool _isClosed;
    private readonly List<string> _transactions = new();

    public string AccountNumber { get; }

    public BankAccount(string accountNumber, decimal openingBalance)
    {
        if (openingBalance < 0)
            throw new ArgumentOutOfRangeException(nameof(openingBalance));

        AccountNumber = accountNumber;
        _balance = openingBalance;
    }

    // 2. Read access is exposed, write access is not
    public decimal Balance => _balance;

    // Callers get a read-only view - they cannot add or remove entries
    public IReadOnlyList<string> Transactions => _transactions;

    // 3. Every change goes through a method that enforces the rules
    public void Deposit(decimal amount)
    {
        EnsureOpen();
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount), "Deposit must be positive.");

        _balance += amount;
        _transactions.Add($"Deposit {amount:C}");
    }

    public bool TryWithdraw(decimal amount)
    {
        EnsureOpen();
        if (amount <= 0 || amount > _balance)
            return false;

        _balance -= amount;
        _transactions.Add($"Withdraw {amount:C}");
        return true;
    }

    public void Close()
    {
        if (_balance != 0)
            throw new InvalidOperationException("Withdraw the remaining balance first.");
        _isClosed = true;
    }

    // 4. Private helper - an implementation detail, not part of the public surface
    private void EnsureOpen()
    {
        if (_isClosed)
            throw new InvalidOperationException("This account is closed.");
    }
}
var account = new BankAccount("GB-001", 100m);
account.Deposit(50m);
Console.WriteLine(account.Balance);            // 150

Console.WriteLine(account.TryWithdraw(500m));  // False - rule enforced
Console.WriteLine(account.TryWithdraw(150m));  // True
account.Close();

// account._balance = 1_000_000m;              // compile error: private
// account.Transactions.Add("fake");           // compile error: IReadOnlyList
// account.Deposit(10m);                       // throws: account is closed
The payoff: one place to look

The balance can now only change inside BankAccount. If a balance is ever wrong, the bug is in this one file - not somewhere in 200,000 lines. That is the whole point of encapsulation.

Access modifiers

Encapsulation is enforced with access modifiers. Default to the most restrictive one that still works.

ModifierWho can access itTypical use
privateOnly the same classDefault for fields and helper methods
publicAny code, any assemblyThe intended API of the class
protectedThe same class and any derived classExtension points for subclasses
internalAny code in the same assembly (project)Types shared inside a library but not exported
protected internalSame assembly or any derived classRare; framework authoring
private protectedDerived classes in the same assemblyRare; tightly controlled inheritance
Defaults worth remembering

A class member with no modifier is private. A top-level class with no modifier is internal. Being explicit is clearer than relying on either.

Levels of exposure

Properties let you pick exactly how much access to give, rather than choosing between "wide open" and "invisible":

public class Order
{
    // Read and write from anywhere
    public string CustomerNote { get; set; }

    // Read anywhere; written only inside this class
    public OrderStatus Status { get; private set; }

    // Set once at creation, then permanently read-only
    public string OrderId { get; init; }

    // Read-only, computed from other state
    public bool IsEditable => Status == OrderStatus.Draft;

    // Not exposed at all - pure internal bookkeeping
    private int _retryCount;

    public void Submit()
    {
        if (!IsEditable)
            throw new InvalidOperationException("Only draft orders can be submitted.");
        Status = OrderStatus.Submitted;      // allowed: we are inside the class
    }
}

public enum OrderStatus { Draft, Submitted, Shipped }
var order = new Order { OrderId = "A-1" };
order.Submit();
Console.WriteLine(order.Status);       // Submitted
// order.Status = OrderStatus.Shipped; // compile error: setter is private

Protecting invariants

An invariant is a statement about an object that must always be true. Encapsulation is how you keep invariants true.

ClassInvariantEnforced by
BankAccountBalance is never negativeTryWithdraw checks before subtracting
OrderOnly draft orders can be editedSubmit checks IsEditable
RectangleWidth and height are positiveConstructor validates, no public setters
DateRangeEnd is never before startConstructor validates both together
 
public class DateRange
{
    public DateOnly Start { get; }
    public DateOnly End { get; }

    public DateRange(DateOnly start, DateOnly end)
    {
        // The two values only make sense checked TOGETHER, which is exactly
        // why they must be set together, in a constructor.
        if (end < start)
            throw new ArgumentException("End cannot be before start.", nameof(end));

        Start = start;
        End = end;
    }

    public int Days => End.DayNumber - Start.DayNumber + 1;
}

Common leaks

A class can be full of private keywords and still leak its internals. Watch for these:

Leak 1: handing out a mutable collection

// BAD - the caller receives the real list and can modify it
public List<string> Items => _items;

// GOOD - expose a read-only view
public IReadOnlyList<string> Items => _items;

// ALSO GOOD - hand out a copy when callers need their own list
public List<string> GetItemsCopy() => new List<string>(_items);

Leak 2: a setter that skips the rules

// BAD - Deposit() validates, but this setter lets callers bypass it entirely
public decimal Balance { get; set; }

// GOOD - read-only property; all writes go through Deposit/TryWithdraw
public decimal Balance => _balance;

Leak 3: anaemic classes (getters and setters, no behaviour)

// BAD - a bag of public data; the rules end up scattered across callers
public class Invoice
{
    public decimal Subtotal { get; set; }
    public decimal Tax { get; set; }
    public decimal Total { get; set; }
}
invoice.Tax = invoice.Subtotal * 0.2m;     // repeated in every caller...
invoice.Total = invoice.Subtotal + invoice.Tax;

// GOOD - the invoice knows how to total itself
public class Invoice
{
    private const decimal VatRate = 0.20m;
    public decimal Subtotal { get; }

    public Invoice(decimal subtotal) => Subtotal = subtotal;

    public decimal Tax => Math.Round(Subtotal * VatRate, 2);
    public decimal Total => Subtotal + Tax;
}
A DTO is the deliberate exception

Classes used purely to carry data across a boundary - API request bodies, database rows, message payloads - are meant to be plain property bags. They have no rules to protect, so they have no behaviour to hold. Do not confuse a DTO with a domain class that does.

A shortcut: records

For immutable value-like data, a record gives you encapsulation with one line - all properties are init-only, and equality compares values rather than references.

public record Money(decimal Amount, string Currency);

var price = new Money(19.99m, "GBP");
// price.Amount = 5m;                      // compile error: init-only

var same = new Money(19.99m, "GBP");
Console.WriteLine(price == same);          // True - value equality
Console.WriteLine(price);                  // Money { Amount = 19.99, Currency = GBP }

// Create a modified copy instead of mutating
var discounted = price with { Amount = 14.99m };
