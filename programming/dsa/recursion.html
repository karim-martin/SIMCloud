Recursion

A method that calls itself. Strange the first time you see it, and then the only sensible way to walk a tree.

Recursion in one sentence

A recursive method solves a problem by calling itself on a smaller version of the same problem, until the problem is small enough to answer outright. Like standing in a queue and asking the person in front "how many people are ahead of you?" - eventually someone at the front can answer without asking anyone.

Every recursive method has two parts

PartJobWhat happens without it
Base caseThe smallest input, answered directly with no further callsThe method never stops - StackOverflowException
Recursive caseCalls itself on a smaller input and builds on the resultIt is not recursion, just a method
 
public static long Factorial(int n)
{
    // BASE CASE - 0! is 1 by definition, no recursion needed
    if (n <= 1) return 1;

    // RECURSIVE CASE - n! is n times (n-1)!, a smaller version of the same problem
    return n * Factorial(n - 1);
}

Console.WriteLine(Factorial(5));   // 120

Watching the call stack

Each call is paused, waiting for the one it made, and its local state is kept on the call stack. Nothing is actually multiplied until the base case returns and the stack unwinds:

Factorial(5)
 └─ 5 * Factorial(4)          <- paused, waiting
     └─ 4 * Factorial(3)      <- paused, waiting
         └─ 3 * Factorial(2)  <- paused, waiting
             └─ 2 * Factorial(1)
                 └─ returns 1          <- BASE CASE reached
             returns 2 * 1  = 2
         returns 3 * 2  = 6
     returns 4 * 6  = 24
 returns 5 * 24 = 120
// Add tracing to see it happen
public static long Factorial(int n, int depth = 0)
{
    string indent = new string(' ', depth * 2);
    Console.WriteLine($"{indent}Factorial({n}) called");

    if (n <= 1)
    {
        Console.WriteLine($"{indent}base case, returning 1");
        return 1;
    }

    long result = n * Factorial(n - 1, depth + 1);
    Console.WriteLine($"{indent}Factorial({n}) returning {result}");
    return result;
}

Worked examples

Sum of a list

public static int Sum(IReadOnlyList<int> numbers, int index = 0)
{
    if (index == numbers.Count) return 0;              // base: nothing left
    return numbers[index] + Sum(numbers, index + 1);   // this one + the rest
}

Console.WriteLine(Sum(new[] { 1, 2, 3, 4 }));          // 10

Reverse a string

public static string Reverse(string s)
{
    if (s.Length <= 1) return s;                       // base: nothing to swap
    return Reverse(s[1..]) + s[0];                     // reverse the tail, append the head
}

Console.WriteLine(Reverse("recursion"));               // noisrucer

Palindrome check

public static bool IsPalindrome(string s)
{
    if (s.Length <= 1) return true;                    // base: trivially symmetric
    if (s[0] != s[^1]) return false;                   // base: ends differ
    return IsPalindrome(s[1..^1]);                     // check the inside
}

Console.WriteLine(IsPalindrome("racecar"));            // True
Console.WriteLine(IsPalindrome("hello"));              // False

Walking a folder tree

This is where recursion stops being a puzzle and becomes the obvious solution - the data itself is nested, so the code that walks it is naturally nested too.

public static long DirectorySize(string path, int depth = 0)
{
    long total = 0;

    foreach (string file in Directory.GetFiles(path))
        total += new FileInfo(file).Length;

    // Each subdirectory is the same problem, one level down
    foreach (string subdirectory in Directory.GetDirectories(path))
        total += DirectorySize(subdirectory, depth + 1);

    Console.WriteLine($"{new string(' ', depth * 2)}{Path.GetFileName(path)}: {total:N0} bytes");
    return total;
}

Walking a tree

// Compare with the loop you would need otherwise: an explicit stack, plus
// bookkeeping for where you were. Recursion hides all of that.
public static int CountNodes<T>(TreeNode<T>? node)
{
    if (node is null) return 0;                                  // base case
    return 1 + CountNodes(node.Left) + CountNodes(node.Right);
}

public static int Height<T>(TreeNode<T>? node)
{
    if (node is null) return -1;
    return 1 + Math.Max(Height(node.Left), Height(node.Right));
}

When recursion goes wrong

The classic naive Fibonacci looks elegant and is catastrophically slow, because it recomputes the same values over and over:

public static long FibSlow(int n)
{
    if (n <= 1) return n;
    return FibSlow(n - 1) + FibSlow(n - 2);     // TWO calls per call - O(2^n)
}

// Fib(40) makes over 300 million calls and takes seconds.
// Fib(50) would take hours.
                    Fib(5)
              /                 \
          Fib(4)               Fib(3)
        /       \             /      \
    Fib(3)     Fib(2)     Fib(2)    Fib(1)
    /    \      /   \      /   \
 Fib(2) Fib(1) ...  ...  ...   ...

Fib(3) computed twice. Fib(2) three times. At n = 40, billions of repeats.

Fix 1: memoisation - remember what you already worked out

public static long FibMemo(int n, Dictionary<int, long>? cache = null)
{
    cache ??= new Dictionary<int, long>();

    if (n <= 1) return n;
    if (cache.TryGetValue(n, out long cached)) return cached;   // seen it before

    long result = FibMemo(n - 1, cache) + FibMemo(n - 2, cache);
    cache[n] = result;                                          // remember it
    return result;
}

Console.WriteLine(FibMemo(90));    // 2880067194370816120 - instant

Each value is now computed exactly once: O(2ⁿ) collapses to O(n). Trading memory for time like this is called dynamic programming.

Fix 2: turn it into a loop

public static long FibIterative(int n)
{
    if (n <= 1) return n;

    long previous = 0, current = 1;

    for (int i = 2; i <= n; i++)
        (previous, current) = (current, previous + current);

    return current;
}

Console.WriteLine(FibIterative(90));   // same answer, O(n) time and O(1) memory

Stack overflow

Every pending call occupies a stack frame, and the stack is roughly 1 MB by default - a few thousand to tens of thousands of frames. Go deeper and the process dies. StackOverflowException cannot be caught in .NET: the process terminates immediately.

// Two ways to blow the stack:

// 1. A missing or unreachable base case
static int Broken(int n) => Broken(n - 1);     // never stops

// 2. A base case that is simply too far away
static long SumTo(int n) => n == 0 ? 0 : n + SumTo(n - 1);
Console.WriteLine(SumTo(100_000));             // crashes - about 100,000 frames

// The iterative version is unbounded and uses one frame
static long SumToIterative(int n)
{
    long total = 0;
    for (int i = 1; i <= n; i++) total += i;
    return total;
}
C# does not guarantee tail-call optimisation

Some languages (F#, Scheme) turn a recursive call in the final position into a loop, making unlimited depth safe. The C# compiler does not promise this. So in C#, recursion depth is a real, hard limit - convert deep recursion to iteration with an explicit Stack<T>.

// Recursive tree walk - fine for a balanced tree, risky for a degenerate one
void WalkRecursive(TreeNode<int>? node)
{
    if (node is null) return;
    Console.WriteLine(node.Value);
    WalkRecursive(node.Left);
    WalkRecursive(node.Right);
}

// Same traversal with an explicit stack - depth limited by memory, not by frames
void WalkIterative(TreeNode<int>? root)
{
    if (root is null) return;

    var stack = new Stack<TreeNode<int>>();
    stack.Push(root);

    while (stack.Count > 0)
    {
        TreeNode<int> node = stack.Pop();
        Console.WriteLine(node.Value);

        if (node.Right is not null) stack.Push(node.Right);   // right first...
        if (node.Left is not null)  stack.Push(node.Left);    // ...so left pops first
    }
}

Divide and conquer

The most productive recursive pattern: split the problem into independent halves, solve each recursively, combine the results. Merge sort and quick sort are both built on it, and so is binary search.

// Maximum of an array, by divide and conquer
public static int Max(int[] a, int low, int high)
{
    if (low == high) return a[low];                    // base: one element

    int mid = low + (high - low) / 2;
    int leftMax  = Max(a, low, mid);                   // solve the left half
    int rightMax = Max(a, mid + 1, high);              // solve the right half

    return Math.Max(leftMax, rightMax);                // combine
}

int[] data = { 3, 9, 2, 8, 5 };
Console.WriteLine(Max(data, 0, data.Length - 1));      // 9

Backtracking

Recursion also drives backtracking: try an option, recurse, and undo it if the path fails. Sudoku solvers, maze solvers, and permutation generators all work this way.

// Every permutation of a string
public static void Permutations(char[] chars, int start = 0)
{
    if (start == chars.Length - 1)                     // base: one arrangement fixed
    {
        Console.WriteLine(new string(chars));
        return;
    }

    for (int i = start; i < chars.Length; i++)
    {
        (chars[start], chars[i]) = (chars[i], chars[start]);   // choose
        Permutations(chars, start + 1);                        // explore
        (chars[start], chars[i]) = (chars[i], chars[start]);   // UNDO - backtrack
    }
}

Permutations("abc".ToCharArray());
// abc, acb, bac, bca, cba, cab
Forgetting to undo is the classic backtracking bug

Without the third line, later branches inherit changes from earlier ones and the output is quietly wrong. Every "choose" needs a matching "un-choose".

Recursion or a loop?

Use recursion whenUse a loop when
The data is nested - trees, folders, JSON, the DOMThe data is flat - arrays, lists, ranges
The problem splits into smaller identical problemsYou are repeating one step a known number of times
Depth is bounded and modest (a tree, not a chain of a million)Depth could be large or unbounded
The recursive version is dramatically clearerThe loop is just as readable
Backtracking is neededRaw performance in a hot path matters

Checklist for writing a recursive method

1

Name the base case first

What is the smallest input you can answer without recursing? Write that line before anything else.

2

Make sure every path shrinks the input

Smaller index, shorter string, one level deeper. If any branch recurses on the same input, it will never terminate.

3

Trust the recursive call

Assume it returns the right answer for the smaller problem, and write the one line that combines it. Do not try to trace every level in your head.

4

Check for repeated work

If the same input can be computed more than once, add memoisation.

5

Estimate the depth

Thousands of frames is fine. Hundreds of thousands is not - convert to iteration.
