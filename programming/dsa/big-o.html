Big-O Notation

Big-O describes how the work an algorithm does grows as the input grows. It is the vocabulary for comparing two solutions.

Big-O in one sentence

Big-O answers "if my data gets ten times bigger, how much slower does this get?" It ignores hardware, language, and constant factors, and describes only the shape of the growth.

Why not just time it?

Because a stopwatch measures your laptop on your data today. Big-O predicts what happens on 10 million rows in production next year. Compare two ways of finding a name:

Items (n)Linear search - stepsBinary search - steps
10104
1,0001,00010
1,000,0001,000,00020
1,000,000,0001,000,000,00030

Binary search is not "a bit faster". It is a different shape of curve, and the gap widens forever.

Reading Big-O

n means "the size of the input". Two rules make Big-O easy to work out by eye:

  • Drop the constants. A loop that does 3 things per item is O(3n), which is written O(n). Big-O compares shapes, not stopwatch readings.
  • Keep only the biggest term. O(n² + n + 100) becomes O(n²), because for large n the square dominates everything else.

The complexity classes you will meet

NotationNameSteps when n = 1,000Typical example
O(1)Constant1Array index, dictionary lookup
O(log n)Logarithmic~10Binary search, balanced tree lookup
O(n)Linear1,000Scanning a list once
O(n log n)Linearithmic~10,000Merge sort, quick sort, Array.Sort

Rule of thumb for interview-sized problems

Up to about 10 million simple operations runs in roughly a second. So O(n log n) is comfortable at n = 1,000,000; O(n²) is fine at n = 1,000 and hopeless at n = 1,000,000.

Each one in C#

O(1) - constant

The work does not depend on the size of the input at all.

int First(int[] numbers) => numbers[0];                 // one index operation

bool HasKey(Dictionary<string, int> map, string key)
    => map.ContainsKey(key);                            // one hash + one probe

// Still O(1): 100 operations is a constant, not a function of n
int Sum3(int[] n) => n[0] + n[1] + n[2];

O(log n) - logarithmic

Each step throws away half the remaining work. Doubling the data adds just one step.

int BinarySearch(int[] sorted, int target)
{
    int low = 0, high = sorted.Length - 1;

    while (low <= high)
    {
        int mid = low + (high - low) / 2;               // half the range each pass
        if (sorted[mid] == target) return mid;
        if (sorted[mid] < target) low = mid + 1;
        else high = mid - 1;
    }
    return -1;
}

O(n) - linear

One pass over the data. Double the data, double the time.

int Max(int[] numbers)
{
    int max = int.MinValue;
    foreach (int n in numbers)                          // touches each item once
        if (n > max) max = n;
    return max;
}

// Two separate loops is O(2n) = still O(n)
int SumThenCount(int[] numbers)
{
    int sum = 0;
    foreach (int n in numbers) sum += n;
    int count = 0;
    foreach (int n in numbers) count++;
    return sum + count;
}

O(n log n) - linearithmic

The realistic best case for a general-purpose sort: n items, each moving through log n levels of splitting.

int[] numbers = { 5, 2, 9, 1, 7 };
Array.Sort(numbers);                          // introsort: O(n log n)

var sorted = numbers.OrderBy(x => x).ToList();// LINQ: also O(n log n)

O(n²) - quadratic

A loop inside a loop over the same data. Fine for hundreds of items; a disaster for millions.

// Every pair compared: n * n = n² steps
bool HasDuplicates(int[] numbers)
{
    for (int i = 0; i < numbers.Length; i++)
        for (int j = i + 1; j < numbers.Length; j++)
            if (numbers[i] == numbers[j]) return true;
    return false;
}

// The SAME job in O(n) using a hash set
bool HasDuplicatesFast(int[] numbers)
{
    var seen = new HashSet<int>();
    foreach (int n in numbers)
        if (!seen.Add(n)) return true;        // Add returns false if already present
    return false;
}
The most valuable trick in this section

Trading memory for speed - keeping a HashSet or Dictionary of what you have already seen - turns an enormous number of O(n²) problems into O(n). It is the first thing to try when a nested loop is too slow.

O(2ⁿ) - exponential

// Each call spawns two more calls: the work doubles with every +1 to n
long Fib(int n) => n <= 1 ? n : Fib(n - 1) + Fib(n - 2);

// Fib(30)  ->  about 1.3 million calls
// Fib(50)  ->  about 2.5 * 10^10 calls: hours of CPU time

Memoisation collapses this back to O(n) by remembering answers already computed.

Best, average, and worst case

An algorithm's cost can depend on the data, not just its size. Big-O usually quotes the worst case, because that is what wakes you at 3am.

OperationBestAverageWorstWorst case happens when
Linear searchO(1)O(n)O(n)The item is last, or missing
Quick sortO(n log n)O(n log n)O(n²)Every pivot is the smallest or largest value
Dictionary lookupO(1)O(1)O(n)Every key hashes into the same bucket
Binary search tree findO(log n)O(log n)O(n)Sorted input turned the tree into a list
List.AddO(1)O(1) amortisedO(n)The internal array is full and must be copied
"Amortised" O(1)

List.Add is usually one instruction, but occasionally the backing array is full and every element is copied to a new, larger one. Because the array doubles, that copy happens rarely enough that the average cost per Add stays constant. That average-over-time guarantee is what "amortised" means.

Space complexity

The same notation applies to memory. Extra memory allocated, not counting the input itself:

// O(1) space - one accumulator regardless of input size
int Sum(int[] numbers)
{
    int total = 0;
    foreach (int n in numbers) total += n;
    return total;
}

// O(n) space - a new collection as large as the input
int[] Doubled(int[] numbers)
{
    var result = new int[numbers.Length];
    for (int i = 0; i < numbers.Length; i++) result[i] = numbers[i] * 2;
    return result;
}

// O(n) space - recursion uses one stack frame per level
int SumTo(int n) => n == 0 ? 0 : n + SumTo(n - 1);

Spotting complexity in real code

You seeUsually
No loopO(1)
One loop over the inputO(n)
Two nested loops over the inputO(n²)
Three nested loopsO(n³)
Halving each pass (n = n / 2)O(log n)
A loop that calls a sort or a binary searchO(n log n)
Two loops one after the otherO(n) - added, not multiplied
A loop over n calling a method that loops over mO(n * m)

Hidden costs that catch people out

The nested loop is not always visible - sometimes it hides inside an innocent-looking method call.

// TRAP 1: Contains on a List is O(n), inside a loop -> O(n * m)
var blocked = new List<string>(/* 10,000 entries */);
foreach (string user in users)
    if (blocked.Contains(user))       // scans all 10,000 EVERY time
        Console.WriteLine(user);

// FIX: a HashSet makes Contains O(1) -> the whole loop is O(n)
var blockedSet = new HashSet<string>(blocked);
foreach (string user in users)
    if (blockedSet.Contains(user))
        Console.WriteLine(user);
// TRAP 2: string concatenation in a loop is O(n²)
// Strings are immutable, so each += copies the whole string so far.
string report = "";
foreach (string line in lines)
    report += line + "\n";            // copies everything, every iteration

// FIX: StringBuilder appends into a buffer -> O(n)
var sb = new StringBuilder();
foreach (string line in lines)
    sb.AppendLine(line);
string report2 = sb.ToString();
// TRAP 3: a LINQ query re-executed on every access
IEnumerable<Order> query = orders.Where(o => o.Total > 100);   // nothing ran yet
Console.WriteLine(query.Count());     // walks the whole sequence
Console.WriteLine(query.First());     // walks it AGAIN

// FIX: materialise once
List<Order> big = orders.Where(o => o.Total > 100).ToList();
// TRAP 4: a database query inside a loop (the "N+1" problem)
foreach (Customer c in customers)                       // 1 query...
    c.Orders = db.Orders.Where(o => o.CustomerId == c.Id).ToList();  // ...+ N queries

// FIX: fetch once, then group in memory
var ordersByCustomer = db.Orders
    .Where(o => customerIds.Contains(o.CustomerId))
    .ToLookup(o => o.CustomerId);
