Sorting Algorithms

Five classic sorts, written out in full, and the one line of C# you should actually ship.

Read this first

In real code you will write list.Sort() and move on. The point of implementing sorts by hand is that they teach the core techniques - swapping, partitioning, divide and conquer, recursion - that turn up everywhere else. Learn them here, use the built-in in production.

Two words you need

TermMeaningWhy you care
StableItems that compare equal keep their original relative orderSort by name, then by department, and names stay alphabetical within each department
In placeSorts using O(1) extra memory, rearranging the original arrayMatters when the data is large relative to available memory

Bubble sort - O(n²)

Repeatedly walk the list, swapping any two neighbours that are in the wrong order. Big values "bubble" to the end. Slow, but the easiest sort to understand.

public static void BubbleSort(int[] a)
{
    for (int pass = 0; pass < a.Length - 1; pass++)
    {
        bool swapped = false;

        // After each pass, the largest remaining item is parked at the end,
        // so the inner loop can stop one place earlier each time.
        for (int i = 0; i < a.Length - 1 - pass; i++)
        {
            if (a[i] > a[i + 1])
            {
                (a[i], a[i + 1]) = (a[i + 1], a[i]);   // tuple swap, C# 7+
                swapped = true;
            }
        }

        if (!swapped) return;      // already sorted - nothing moved this pass
    }
}

int[] data = { 5, 2, 9, 1, 7 };
BubbleSort(data);
Console.WriteLine(string.Join(" ", data));   // 1 2 5 7 9
Start:  5 2 9 1 7
Pass 1: 2 5 9 1 7 -> 2 5 1 9 7 -> 2 5 1 7 [9]
Pass 2: 2 1 5 7 [9]
Pass 3: 1 2 5 7 [9]
Pass 4: no swaps - stop early

Best O(n) (already sorted, thanks to the early exit), average and worst O(n²), stable, in place.

Selection sort - O(n²)

Find the smallest remaining item and swap it into the next position. Always exactly n-1 swaps, which is its one selling point when writes are expensive.

public static void SelectionSort(int[] a)
{
    for (int i = 0; i < a.Length - 1; i++)
    {
        int minIndex = i;

        // Scan the unsorted remainder for the smallest value
        for (int j = i + 1; j < a.Length; j++)
            if (a[j] < a[minIndex]) minIndex = j;

        if (minIndex != i)
            (a[i], a[minIndex]) = (a[minIndex], a[i]);
    }
}

O(n²) in every case - it always scans the remainder, even on sorted input. Not stable, in place.

Insertion sort - O(n²), but fast where it counts

How most people sort a hand of playing cards: take the next item and slide it back into its place among the already-sorted ones.

public static void InsertionSort(int[] a)
{
    for (int i = 1; i < a.Length; i++)
    {
        int current = a[i];
        int j = i - 1;

        // Shift everything larger than "current" one place right
        while (j >= 0 && a[j] > current)
        {
            a[j + 1] = a[j];
            j--;
        }

        a[j + 1] = current;      // drop it into the gap
    }
}
Why insertion sort still matters

It is O(n) on nearly-sorted data and has tiny constant overhead, so it beats the clever sorts on small arrays. Production sorts - including .NET's - switch to insertion sort once a partition drops below about 16 elements.

Best O(n), average and worst O(n²), stable, in place.

Merge sort - O(n log n)

public static int[] MergeSort(int[] a)
{
    if (a.Length <= 1) return a;              // base case: already sorted

    int mid = a.Length / 2;
    int[] left  = MergeSort(a[..mid]);        // sort the first half
    int[] right = MergeSort(a[mid..]);        // sort the second half

    return Merge(left, right);
}

private static int[] Merge(int[] left, int[] right)
{
    var result = new int[left.Length + right.Length];
    int i = 0, j = 0, k = 0;

    // Repeatedly take the smaller of the two front items
    while (i < left.Length && j < right.Length)
    {
        // "<=" keeps equal items in their original order, which makes this stable
        result[k++] = left[i] <= right[j] ? left[i++] : right[j++];
    }

    // One side is exhausted - copy whatever remains of the other
    while (i < left.Length)  result[k++] = left[i++];
    while (j < right.Length) result[k++] = right[j++];

    return result;
}

int[] sorted = MergeSort(new[] { 38, 27, 43, 3, 9, 82, 10 });
Console.WriteLine(string.Join(" ", sorted));   // 3 9 10 27 38 43 82

O(n log n) in every case - log n levels of splitting, n work to merge each level. Stable, but needs O(n) extra memory. That predictability is why it is used for external sorts (data too big for RAM) and stable sorts in Java and Python.

Quick sort - O(n log n) average

Pick a pivot, move everything smaller to its left and everything larger to its right (so the pivot is now in its final position), then sort the two sides the same way.

public static void QuickSort(int[] a) => QuickSort(a, 0, a.Length - 1);

private static void QuickSort(int[] a, int low, int high)
{
    if (low >= high) return;                 // 0 or 1 element: done

    int pivotIndex = Partition(a, low, high);
    QuickSort(a, low, pivotIndex - 1);       // everything left of the pivot
    QuickSort(a, pivotIndex + 1, high);      // everything right of it
}

// Lomuto partition: use the last element as the pivot
private static int Partition(int[] a, int low, int high)
{
    int pivot = a[high];
    int boundary = low - 1;                  // end of the "smaller than pivot" region

    for (int i = low; i < high; i++)
    {
        if (a[i] <= pivot)
        {
            boundary++;
            (a[boundary], a[i]) = (a[i], a[boundary]);
        }
    }

    // Put the pivot immediately after the smaller region - its final place
    (a[boundary + 1], a[high]) = (a[high], a[boundary + 1]);
    return boundary + 1;
}

int[] data = { 38, 27, 43, 3, 9, 82, 10 };
QuickSort(data);
Console.WriteLine(string.Join(" ", data));    // 3 9 10 27 38 43 82
Quick sort's worst case

If every pivot turns out to be the smallest or largest remaining value, the partitions are of size 0 and n-1, and the cost degrades to O(n²). With "last element as pivot", already sorted input triggers exactly that. Real implementations pick the median of three candidates, or a random index:

private static int Partition(int[] a, int low, int high)
{
    // Choose a random pivot and move it out of the way first.
    // Sorted or reverse-sorted input is no longer a special case.
    int random = Random.Shared.Next(low, high + 1);
    (a[random], a[high]) = (a[high], a[random]);

    // ...then partition exactly as before
    int pivot = a[high];
    int boundary = low - 1;

    for (int i = low; i < high; i++)
    {
        if (a[i] <= pivot)
        {
            boundary++;
            (a[boundary], a[i]) = (a[i], a[boundary]);
        }
    }

    (a[boundary + 1], a[high]) = (a[high], a[boundary + 1]);
    return boundary + 1;
}

Best and average O(n log n), worst O(n²), not stable, sorts in place (O(log n) stack space). Usually the fastest general-purpose sort in practice, because partitioning is cache-friendly and needs no extra array.

What to actually use

.NET's Array.Sort and List<T>.Sort use introsort: quick sort, switching to heap sort if the recursion goes too deep (removing the O(n²) worst case) and to insertion sort on small partitions. You will not beat it by hand.

// In place - fastest, mutates the original
int[] numbers = { 5, 2, 9, 1 };
Array.Sort(numbers);                          // 1 2 5 9

var list = new List<string> { "pear", "apple", "fig" };
list.Sort();                                  // apple, fig, pear

// Custom order with a lambda comparison
var people = new List<(string Name, int Age)>
{
    ("Ada", 36), ("Alan", 41), ("Grace", 45)
};
people.Sort((x, y) => x.Age.CompareTo(y.Age));            // youngest first
people.Sort((x, y) => y.Age.CompareTo(x.Age));            // oldest first

// LINQ - returns a NEW sequence, leaves the original untouched, and is stable
var byAge = people.OrderBy(p => p.Age).ToList();
var byNameThenAge = people.OrderBy(p => p.Name).ThenByDescending(p => p.Age).ToList();

// .NET 7+ shorthand for OrderBy(x => x) on a self-comparable sequence
var sortedNumbers = numbers.Order().ToList();

Sorting your own types

// Option 1: IComparable<T> - the type's natural order
public class AppVersion : IComparable<AppVersion>
{
    public int Major { get; init; }
    public int Minor { get; init; }

    public int CompareTo(AppVersion? other)
    {
        if (other is null) return 1;
        int byMajor = Major.CompareTo(other.Major);
        return byMajor != 0 ? byMajor : Minor.CompareTo(other.Minor);
    }

    public override string ToString() => $"{Major}.{Minor}";
}

var versions = new List<AppVersion>
{
    new() { Major = 2, Minor = 1 },
    new() { Major = 1, Minor = 9 },
    new() { Major = 2, Minor = 0 }
};
versions.Sort();                              // uses CompareTo: 1.9, 2.0, 2.1

// Option 2: IComparer<T> - an alternative order, without touching the type
public class DescendingVersionComparer : IComparer<AppVersion>
{
    public int Compare(AppVersion? x, AppVersion? y) => y!.CompareTo(x!);
}

versions.Sort(new DescendingVersionComparer());   // 2.1, 2.0, 1.9
The comparison contract

CompareTo returns a negative number if this instance sorts before the other, zero if they are equivalent, and a positive number if it sorts after. Be consistent - an inconsistent comparer makes Array.Sort throw InvalidOperationException or produce nonsense.

Practical rules

SituationDo this
Ordinary application codeArray.Sort, List.Sort, or OrderBy
You need the original order preservedOrderBy - it is stable and returns a new sequence
You only need the top 10 of a millionA heap or OrderBy(...).Take(10) - do not sort everything by hand
Data comes from a databaseSort in SQL with ORDER BY; the index is already there
Sorting inside a loopSort once outside the loop
Sorting to then search repeatedlyConsider a Dictionary instead - O(1) beats O(log n)
