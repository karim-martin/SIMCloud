Searching Algorithms

Finding one item among many. The method you choose decides whether that takes a million steps or twenty.

The whole page in one idea

Looking for a name in an unsorted pile means checking every sheet. Looking for it in a phone book means opening the middle, deciding "earlier" or "later", and throwing away half the book each time. Same task, wildly different amounts of work - the difference is whether the data is organised.

Linear search - O(n)

Start at the beginning, check each item, stop when you find it. It works on anything - sorted or not, array or linked list - and it is the only option when the data has no order.

public static int LinearSearch<T>(IList<T> items, T target)
{
    for (int i = 0; i < items.Count; i++)
        if (EqualityComparer<T>.Default.Equals(items[i], target))
            return i;                          // found: return the position

    return -1;                                 // conventional "not found"
}

int[] data = { 5, 2, 9, 1, 7 };
Console.WriteLine(LinearSearch(data, 9));      // 2
Console.WriteLine(LinearSearch(data, 4));      // -1

Best case 1 comparison (the first item); worst case n (the last item, or absent). On average, half the collection - which is still O(n).

// The .NET equivalents, all O(n) on a List or array
int index   = Array.IndexOf(data, 9);                    // 2
bool exists = data.Contains(9);                          // True
int? first  = data.FirstOrDefault(x => x > 6);           // 9
int found   = Array.Find(data, x => x % 2 == 0);         // 2
int[] all   = Array.FindAll(data, x => x > 4);           // 5, 9, 7

Binary search - O(log n)

Requires the data to be sorted. Look at the middle item; if it is too small, the answer must be in the right half, so discard the left half entirely. Repeat.

Finding 23 in [2, 5, 8, 12, 16, 23, 38, 56, 72, 91]
low=0, high=9, mid=4 → 16
23 > 16, so search the right half
discard indexes 0-4
low=5, high=9, mid=7 → 56
23 < 56, so search the left half
discard indexes 7-9
low=5, high=6, mid=5 → 23
found, in 3 comparisons instead of 6
public static int BinarySearch(int[] sorted, int target)
{
    int low = 0;
    int high = sorted.Length - 1;

    while (low <= high)                       // "<=" - a single-item range is still valid
    {
        // NOT (low + high) / 2 - that can overflow int on huge arrays
        int mid = low + (high - low) / 2;

        if (sorted[mid] == target) return mid;

        if (sorted[mid] < target) low = mid + 1;    // answer is in the right half
        else                      high = mid - 1;   // answer is in the left half
    }

    return -1;
}

int[] sorted = { 2, 5, 8, 12, 16, 23, 38, 56, 72, 91 };
Console.WriteLine(BinarySearch(sorted, 23));   // 5
Console.WriteLine(BinarySearch(sorted, 91));   // 9
Console.WriteLine(BinarySearch(sorted, 40));   // -1

The recursive version

public static int BinarySearchRecursive(int[] sorted, int target, int low, int high)
{
    if (low > high) return -1;                 // base case: the range is empty

    int mid = low + (high - low) / 2;

    if (sorted[mid] == target) return mid;     // base case: found it

    return sorted[mid] < target
        ? BinarySearchRecursive(sorted, target, mid + 1, high)
        : BinarySearchRecursive(sorted, target, low, mid - 1);
}

Console.WriteLine(BinarySearchRecursive(sorted, 23, 0, sorted.Length - 1));   // 5

Both versions do the same work; the iterative one uses O(1) space rather than O(log n) stack frames. Prefer it.

Three classic bugs

1. while (low < high) instead of <= - misses the target when the range narrows to one item.
2. low = mid instead of mid + 1 - the range stops shrinking and the loop never ends.
3. (low + high) / 2 - overflows to a negative number once the indexes exceed about 1.07 billion. This bug sat in the JDK for nine years.

The built-in

int[] sorted = { 2, 5, 8, 12, 16, 23, 38 };

int i = Array.BinarySearch(sorted, 16);        // 4
Console.WriteLine(i);

// Not found: returns the bitwise complement of where it WOULD go.
int missing = Array.BinarySearch(sorted, 20);  // -6
int insertAt = ~missing;                       // 5 - handy for ordered inserts
Console.WriteLine($"Insert 20 at index {insertAt}");

var list = new List<int>(sorted);
int j = list.BinarySearch(38);                 // 6
The data really must be sorted

Array.BinarySearch on unsorted data does not throw - it quietly returns a wrong answer. If you sort in order to search once, you have spent O(n log n) to save O(n): just scan it.

Hash lookup - O(1)

The fastest option of all, if you can build the index up front. See Hash Tables for how it works.

var customers = new List<Customer>(/* 100,000 items */);

// Build the index ONCE - O(n)
Dictionary<int, Customer> byId = customers.ToDictionary(c => c.Id);

// Then every lookup is O(1), however many you do
if (byId.TryGetValue(98_765, out Customer? customer))
    Console.WriteLine(customer.Name);

// Membership only? A set is smaller and clearer
var activeIds = new HashSet<int>(customers.Where(c => c.IsActive).Select(c => c.Id));
Console.WriteLine(activeIds.Contains(98_765));

Which to use

MethodTimeNeedsSetup costUse when
Linear searchO(n)NothingNoneSmall data, or a one-off lookup
Binary searchO(log n)Sorted dataO(n log n) to sortSorted data you search repeatedly, or need a range from
Hash lookupO(1)A dictionary or set, and hashable keysO(n) to build, O(n) memoryMany lookups by exact key
Tree lookupO(log n)SortedDictionary / SortedSetO(n log n) to buildLookups plus ordered iteration and range queries
Database indexO(log n)An index on the columnCreated once by the DBAThe data lives in a database - do not pull it into memory to scan it
The decision that matters most

Count how many times you will search. Once - just scan; building an index costs more than the scan saves. Many times - build a Dictionary or HashSet first. This one judgement fixes more slow code than any other single change.

Useful binary-search variants

Binary search does more than find one exact match. The same halving works on any question with a yes/no answer that flips exactly once across the range.

// Find the FIRST index whose value is >= target (a "lower bound").
// Useful for range queries: everything from here on is >= target.
public static int LowerBound(int[] sorted, int target)
{
    int low = 0, high = sorted.Length;         // note: high is one PAST the end

    while (low < high)
    {
        int mid = low + (high - low) / 2;
        if (sorted[mid] < target) low = mid + 1;
        else                      high = mid;  // mid might be the answer - keep it
    }

    return low;                                // == Length if every value is smaller
}

int[] data = { 1, 3, 3, 3, 5, 8 };
Console.WriteLine(LowerBound(data, 3));        // 1 - the first 3
Console.WriteLine(LowerBound(data, 4));        // 4 - where 4 would be inserted
Console.WriteLine(LowerBound(data, 9));        // 6 - past the end
// Binary search over an ANSWER, not an array.
// "What is the smallest number of machines that can process the load in time?"
// CanFinish(jobs, machines, hours) is your own feasibility check - it only has
// to answer yes/no, and the answer must flip once as "machines" increases.
int MinimumMachines(int[] jobs, int hoursAvailable)
{
    int low = 1, high = jobs.Length;           // 1 machine per job is always enough

    while (low < high)
    {
        int mid = low + (high - low) / 2;
        if (CanFinish(jobs, mid, hoursAvailable)) high = mid;   // try fewer
        else                                     low = mid + 1; // need more
    }

    return low;
}

Searching text

string text = "the quick brown fox";

Console.WriteLine(text.Contains("brown"));                     // True
Console.WriteLine(text.IndexOf("brown"));                      // 10
Console.WriteLine(text.IndexOf("BROWN", StringComparison.OrdinalIgnoreCase));  // 10
Console.WriteLine(text.StartsWith("the"));                     // True
Console.WriteLine(text.LastIndexOf('o'));                      // 17

// Pattern matching with a regular expression
var match = System.Text.RegularExpressions.Regex.Match(text, @"\b\w{5}\b");
Console.WriteLine(match.Value);                                // quick
Always specify a StringComparison

Culture-sensitive comparison is the default for some string methods and is both slower and locale-dependent. For identifiers, keys, and file paths use StringComparison.Ordinal or OrdinalIgnoreCase; reserve culture-aware comparison for text shown to users.
